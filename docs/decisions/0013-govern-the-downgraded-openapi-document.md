# 0013 — Govern the downgraded OpenAPI 3.0.3 document under ADR 0007's rules

**Status:** accepted (2026-08-14)
**Date:** 2026-08-14
**Chunk:** 02 (recorded); implemented in 09
**Extends:** [0007](0007-commit-the-generated-discovery-artifacts.md) ·
**Depends on:** [0001](0001-generate-openapi-from-the-operation-registry.md)

## Context

[ADR 0007](0007-commit-the-generated-discovery-artifacts.md) decided that
generated discovery artifacts are **committed** to each service, and attached
four rules to that decision: never ship them as template files, regenerate
and fail on drift in `make agents-docs`, mark them `-merge` in
`.gitattributes`, and keep the runtime endpoints registry-derived rather than
file-derived.

It named two files: `openapi.json` and `llms.txt`.

[ADR 0001](0001-generate-openapi-from-the-operation-registry.md) was written
in parallel and produced a **third** generated file. `oapi-codegen` v2.5.0
cannot read OpenAPI 3.1 at all — 3.1 made `exclusiveMinimum` a number and
`kin-openapi` still models it as the 3.0 boolean — so 0001 requires emitting
a mechanically downgraded 3.0.3 copy alongside the canonical 3.1 document.
FastAPI's own 3.1 output fails identically, so this is an ecosystem gap that
every generated service inherits.

Neither ADR mentions the other. The downgraded file currently has no
governing rules at all.

## Decision

**The downgraded document is governed by ADR 0007's four rules, unchanged.**
It is committed, never a template file, `-merge` in `.gitattributes`,
regenerated by `make agents-docs`, and covered by the drift check.

Name it `openapi-3.0.json`, beside `openapi.json`. The name states what it is
without a reader having to open it.

**`/openapi.json` serves the 3.1 document only.** The 3.0 copy is a build
artifact for client generators, not a second API surface — there is no
`/openapi-3.0.json` endpoint. A consumer that needs it fetches it from the
repo, which is precisely the case for committing it.

## Alternatives considered

**Leave it ungoverned and let chunk 09 decide.** This is what would have
happened by default, and it is how a file ends up committed by one service,
gitignored by another, and stale in a third. The rules exist; extending them
costs one sentence.

**Gitignore the 3.0 copy while committing the 3.1 one.** Superficially
attractive — it *is* derived from a derived file. But the consumer who needs
it is an external client-generator user who has checked out the repo and is
not going to install Go, uv and the service's whole toolchain to run `make
agents-docs`. Committing it is the entire reason it is useful.

**Serve it at `/openapi-3.0.json` too.** Rejected: two live endpoints for the
same API is two things to keep in sync at runtime, to document, and to
explain. The 3.1 document is the API's description; the 3.0 file is a
compatibility shim for one tool.

**Emit 3.0.3 as canonical and skip 3.1 entirely.** Tempting, since 3.0 is
what `oapi-codegen` reads. Rejected because 3.1 is the version aligned with
JSON Schema 2020-12, `openapi-typescript` consumes it natively, and
downgrading is mechanical while upgrading is not. Making the lossy artifact
canonical to satisfy one tool's lag would outlive the lag.

## Consequences

`make agents-docs` produces three files and the drift check covers three.
The parity assertion added in chunk 02 must match `openapi*.json`, not just
`openapi.json` — it already does.

When `kin-openapi` gains 3.1 support, this ADR gets superseded and the 3.0
file deleted. That is a clean removal: one generator step, one committed
file, one README paragraph, and nothing depends on it at runtime by
construction.

The generated README must state plainly that Go client generation uses
`openapi-3.0.json`. Consumers will otherwise hit `json: cannot unmarshal
number into field Schema.exclusiveMinimum of type bool` and reasonably
conclude the spec is broken.
